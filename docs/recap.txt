Ceci est un projet d'étude visant a explorer la structure des executables et la manière dont Linux les execute.

L'idée est de créer un simple packer inspiré de UPX pour mettre en pratique les notions que j'ai pu apprendre grace
aux cours de l'excellente plateforme OpenSecurityTraining (cours Life of Binaires).

-Qu'est ce qu'un packer ?
Un packer est un outil qui transforme un fichier exécutable en compressant ou en chiffrant son contenu, afin de réduire
sa taille ou de compliquer son analyse, tout en préservant son comportement originel grâce à un mécanisme de dépaquetage.

-Strategie de packing
Beaucoup de stratégies existent, certaines très simples et d'autres plus complexes. Dans le cadre de ce projet, afin de réellement toucher
a toutes les notions importantes nous nous intereserons a la methodologie employee par le packer open source UPX.

Cette strategie consiste sommairement en les etapes suivante :
- Le packer ouvre le fichier executable qu'il doit packer et le chiffre/compresse.
- Il cree un nouveau fichier et insere cette data chiffrée/compressée à l'intérieur.
- Il insere également du code executable (qu'on appellera stub) qui a pour but de trouver décompresser/déchiffrer et
  d'executer la data originelle.
- Nous avons donc en sortie un nouvel executable avec comme seul code analysable le stub de déchiffrement et chargement.
  Le code originel est completement opaque et leger.
- Lors de l'execution le stub sera executé en premier, et, une fois déchifré l'executable originel sera executé de maniere
  identique a son état originel (tout ceci uniquement en RAM, sans créer de fichier temporaire, donc pas d'execve classique).

Pour accomplir ceci, nous devons donc comprendre les choses suivantes :
- Quelle est la structure d'un executable linux (ELF).
- Comment un executable est "executé".
- ....

Avant de commencer, il nous faut expliquer rapidement comment fonctionne l'adressage virtuel sous Linux.

La RAM physique de notre ordinateur est principalement gérée par le kernel. Celui-ci s'occupe notamment d'attribuer de la mémoire aux différents processus
et d'optimiser son utilisation en arrière-plan (en regroupant les données pour défragmenter par exemple) sans que nous nous en rendions compte.

Mais cela peut paraître inquiétant lorsque nous développons un programme qui utilise cette RAM.
Un développeur ne veut surtout pas que ses pointeurs se retrouvent invalidés simplement parce que le kernel a eu besoin de déplacer ses données
ailleurs en mémoire physique, n'est-ce pas ?

Pour pallier ce problème (entre autres), les systèmes modernes utilisent un mécanisme appelé mémoire virtuelle.

La mémoire virtuelle

En vulgarisant on peut dire qu'une adresses virtuelle est simplement un "nombre/identifiant" servant a retrouver la bonne
adresse physique. Sur les architectures x86-64, elles sont représentées sur 64 bits et sont comprises généralement dans
une plage allant de 0x0000000000010000 à 0x00007fffffffefff (ces limites dépendent de la configuration du système).

Lorsque Linux exécute un processus, il lui fournit un ensemble de structures appelées "page tables" (nous ne rentrerons pas dans
les détails techniques ici).
Ces structures ont pour but de faire le lien entre les adresses virtuelles et les adresses physiques au sein d'un processus.
A l'intérieur de ces tables, chaque adresse virtuelle se voit en général attribuée un adresse physique dans la RAM (voir NOTE).
Si le kernel a besoin de réorganiser la RAM, il n'aura qu'a mettre a jour l'adresse physique associée à l'adresse virtuelle.
Ainsi, lorsqu'on "déréférence" une adresse virtuelle, le processeur va chercher les données présentes à l'adresse physique
associée à cette adresse virtuelle (ou déclancher un PAGE FAULT dans le cas ou aucne adresse physique n'est spécifiée).

Lorsqu'on parle d'"adresses" en programmation, on parle pratiquement toujours d'adresses virtuelles.

Chaque processus possède ses propres page tables indépendantes. Cela signifie que deux processus peuvent parfaitement utiliser
la même adresse virtuelle, par exemple 0x400000, sans pour autant accéder aux mêmes données.

Les pages mémoire

Pour comprendre totalement ce mécanisme, il faut introduire le concept de page mémoire.
Nous avons dit que "une adresse virtuelle" -> "une adresse physique".
En réalité, il s'agit plutôt de "une page virtuelle" -> "une page physique".

Une page est simplemnt un "bloc de mémoire de taille fixe". Sur x86-64, ce bloc est en général de 0x1000 bytes (4096).
Le kernel travaille avec des pages de RAM (page frames) plutot qu'avec des adresses isolées.
Donc lorsque le kernel doit allouer de la mémoire pour un processus, il lui attribue un nombre depages en fonction du besoin,
et non pas exactement le nombre de bytes réellement nécessaires.
Exemple :
Besoin de 0x2431 --> on arrondit à 3 pages de 0x1000.

Attention : ici, nous parlons de l'allocation de mémoire nécessaire à l'établissement du contexte d'exécution d'un processus,
et non de l'allocation de mémoire de travail par le programme pendant son exécution (via malloc(), par exemple).
Dans ce second cas, la mémoire demandée peut déjà être disponible dans une région précédemment réservée (le kernel n'alloue pas
de nouvelles pages a chaque malloc(), la heap agit comme une sorte réserve de mémoire). Si ce n'est pas le cas, de nouvelles pages
virtuelles peuvent être demandées au kernel.

Donc pour préciser ce qui à été dit plus haut : les pages tables permettent de relier les pages virtuelles aux pages physiques.
Pour simplifier, nous pouvons imaginer ces tables représentent un grand dictionnaire contenant des paires « key/value » :

Key : l'adresse de début d'une page virtuelle.
Value : l'adresse physique du page frame correspondant.

Prenons un exemple avec deux processus différents :

Processus A :
0x400000 → 0x12A000
0x401000 → 0x31000

Processus B :
0x400000 → 0x58000
0x401000 → 0x92000

Nous remarquons que les deux processus utilisent exactement les mêmes adresses virtuelles, mais que celles-ci correspondent à des emplacements physiques différents.
Imaginons maintenant que le processus A tente de lire les données situées à l'adresse virtuelle 0x400123.
Le processeur identifie la page virtuelle contenant cette adresse (0x400000), retrouve son page frame correspondant (0x12A000), puis y ajoute le décalage de 0x123 octets.
Notre lecture s'effectuera donc à l'adresse physique 0x12A123.
Cette traduction est effectuée automatiquement par un composant matériel du processeur appelé MMU (Memory Management Unit).

Cette implémentation permet également d'autres avantages.
Par exemple, deux processus peuvent posséder chaqu'un une page virtuelle qui correspond a la meme page physique. Cela permet notamment de partager le
code des bibliothèques partagées entre plusieurs processus, sans avoir besoin de le dupliquer en RAM. Ceci autorise également deux pages virtuelles consécutives
à correspondre à deux page frames physiques très éloignés. Un programme peut donc manipuler une plage d'adresses virtuelles continue, même si les données
correspondantes sont dispersées dans la RAM physique.
Exemple :

Processus :
0x400000 → 0x12A000
0x401000 → 0x31000

Si notre programme utilise un ptr = 0x400900, il peu très bien l'incrémenter jusqu'à dépasser 0x401000, même si le page frame physique de ces deux pages n'est pas
contigu. Lorsque le processeur déréférencera ce pointeur, il trouvera automatiquement la bonne adresse physique.

NOTE: Les page tables ne sont pas de simples dictionnaires « key/value ». Ce sont des structures hiérarchiques beaucoup plus complexes, contenant également des informations
	  sur les permissions d'accès aux pages (plus d'info ici https://docs.kernel.org/mm/page_tables.html).
	  De plus, une page virtuelle ne possède pas nécessairement un page frame associé à tout instant : par exemple, pour optimiser, certaines pages peuvent ne pas encore
	  avoir été chargées en RAM et ne le seront que lorsqu'on en a explicitement besoin.
	  Enfin, les exemples précédents utilisent des pages de 0x1000, mais x86-64 prend également en charge des pages plus grandes.
	  Cependant, pour comprendre les opérations de mapping effectuées dans le cadre de ce projet, le modèle simplifié présenté ici est suffisant.

Format ELF (Executable and Linking Format)

Ici nous traiterons uniquement le cas ELF x86-64.

Un fichier ELF n'est pas directement du code machine destiné au processur. C'est avant tout un format de fichier qui permet de stocker du
code machine, des données, ainsi que des informations décrivant comment ces éléments doivent être interprétés.

Un ELF peut représenter plusieurs choses. Les plus communes sont :
- Executable: Un programme destiné à être exécuté par le système.
- Shared object (.so): Une bibliothèque dont le code peut être chargé et utilisé par d'autres programmes. Souvent les .so ne sont pas executables independamment.
- Relocatable object (.o): Un fichier contenant du code compilé, mais qui doit être linké pour être intégré à un programme.

Sections et Segments

Lors de la compilation d'un programme, le compilateur et le linker organisent son contenu en différentes parties appelées sections.
Chaque section contient de la data spécifique.

Quelques exemples classiques de sections générées automatiquement par presque tous les compilateurs/linkers :
- ".text" contient généralement les instructions machine du programme.
- ".rodata" contient généralement des données en lecture seule.
- ".data" contient généralement des données initialisées qui peuvent être modifiées pendant l'exécution.

NOTE: Il n'y a aucune règle de nommage officielle pour les sections.

Cette organisation par sections est très utile lors du linking de différents fichiers objets en un executable final. Le linker peut par
exmple retrouver l'ensemble du code machine des tous les objets et l'unir ensemble dans le .text final de l'executable, ou encore
exclure de l'ELF final des sections entieres qui ne servaient que pour la construction.
De la même maniere, cette organisation peremet a différents outils Linux de parser rapidement et simplement les differents contenus d'un ELF
(readelf, objdump...).

Cependant, les sections ne servent que pour la construction et l'analyse d'un ELF. Le kernel n'a aucunement besoin de connaitre cette subdivision
en sections. Tout ce qui lui importe c'est : quelles parties du fichier faut il charger en mémoire, et comment interpreter ces bouts de fichier
chargés.

Une autre manière d'organiser la data est donc nécessaire : les segments.

Un segment est essentiellement une zone contigue de données. Ce terme est utilisé pour designer une zone du fichier ELF, le plus souvent en englobant
une ou plusieurs sections. Lors du chargement, certains de ces segments sont traités par le système pour charger en mémoire les données nécessaires
à l'execution. On utilise le terme segment pour designer aussi bien une zone de données d'un ELF sur disque, que la representation de cette zone
en mémoire, lorsqu'elle est chargée.

Organisation de la structure ELF

Nous pouvons distinguer 4 éléments principaux :

- HEADER  [IMAGE HEADER]
  Il s'agit d'une structure de taille fixe située au tout début du fichier.
  Il contient les caractéristiques générales de l'ELF, comme son architecture, son type, ou encore la position de la Section Header Table
  et de la Program Header Table.
  C'est en quelque sorte le point de départ permettant d'interpréter le reste du fichier.

- PROGRAM HEADER TABLE [IMAGE PHDR]
  Il s'agit d'un tableau de structures appellées Program Header.
  Un Program Header contient des informations destinées a être lues par le chargeur du système : l'adresse de chargement de certains
  segments, leurs permissions, leur zone de chargement...
  Chaque Program Header peut désigner un segment (donc une zone contigue de l'ELF), un segment chargeable (donc un segment qui doit être
  chargé en mémoire), ou de la métadonée de chargement qui ne représente aucune zone de l'ELF, simplement des informations sur comment
  gérer le chargement et l'execution.
  Bien que ce ne soit pas une règle officielle, la Program Header Table se situe souvent avant la Data, juste après le Header.
  Il existe de nombreux types (p_type) de Program Headers, mais dans le cadre de ce write-up nous nous interesserons seulement aux suivants :
  - PT_LOAD: Le plus important. Cet header decrit un segment de l'ELF qui sera chargé en mémoire. A noter qu'il est très fréquent que
	ce type de segment couvre plusieurs autres segments plus petis. Le premier segment PT_LOAD d'un ELF comprend souvent au moins le
	segment PT_PHDR et PT_INTERP.
  - PT_PHDR: Decrit un segment qui contient l'entièreté des entrées de la Program Header Table.
  - PT_INTERP: Decrit un segment qui contient le nom absolu d'un exectuable ELF qui jouera le role d'interpreteur (cette notion sera expliquée
  	plus tard).
  - PT_DYNAMIC: Decrit un segment qui contient la section .dynamic. Cette section fournit des informations nécessaires à la liaison dynamique.
	Elle permet notamment de savoir quelles bibliothèques partagées (.so) doivent être chargées et contient les informations pour retrouver
	les adresse mémoire des fonctions qu'elles exportent. Nous nous interesserons un peu plus en détails a cette fonction plus tard.
  - PT_GNU_STACK: Ce Program Header ne decrit aucun segment, il renseigne seulement un flag qui indique si la stack qu'un ELF  va avoir
    lors de son execution doit être executable ou non (si ce n'est pas clair, ça le sera plus tard).

- DATA
  C'est le contenu du fichier : instructions machine, constantes, variables initialisées, informations de symboles, etc.
  La majorité est rangée par sections, qui peuvent a leur tour être regroupées par segments.

- SECTION HEADER TABLE [IMAGE SHDR]
  Il s'agit d'un tableau de structures appellées Section Header.
  Un Section Header décrit une section: sa position, sa taille, son type et différentes propriétés.
  Cette table n'est pas utilisée par le chargeur du système, et peut donc être absente sans poser de problèmes d'execution.
  La premiere entrée de cette table est toujours nulle.
  Le plus souvent, la Section Header Table est placée après la Data, à la fin du fichier, mais ce n'est pas une obligation.

[image structure elf]

NOTE: On remarque que le Header et la Program Header Table font partie d'un segment sans pour autant faire partie d'une section.

Ce qu'il faut retenir ici est que les Sections Headers et Program Headers se partagent globalement la meme donnée. Ce sont simplement des structures qui subdivisent
l'ELF de maniere differente. Cela permet deux lectures differentes, une qui sert a executer l'ELF et l'autre qui sert a le construire.

Nous allons maintenant entrer un peu plus dans les details d'un Prgoram Header.

Program Header

Lorsqu'on utilise `readelf -lW` pour afficher la Program Header Table, on obtient quelque chose comme ça :
[readelf image]

Exliquons brièvement chaqu'un des champs:

p_type:		Indique le type de du Program Header, comme PT_LOAD, PT_PHDR, PT_INTERP... Les differents types sont consultables ici
			https://github.com/torvalds/linux/blob/master/include/uapi/linux/elf.h. D'autres types existent pour d'autres architecture,
			mais dans le cadre de ce projet nous utilierons ce header comme référence.
p_offset:	Indique à quel offset du fichier se trouve le debut de la zone de données couverte par le segment.
p_vaddr:	Indique l'adresse mémoire (virtuelle) à laquelle la data couverte par ce segment se trouve en mémoire. Pour les exécutables de
			type PIE, cette adresse est relative à une adresse de base déterminée lors du chargement (pas d'inquiétudes, on va clarifier après).
p_paddr:	Indique l'adresse physique du segment sur les systèmes qui utilisent cette information. Sous Linux, pour les exécutables
			classiques en espace utilisateur, ce champ est ignoré. Il est souvent initialisé à la même valeur que p_vaddr.
p_filesz:	Indique la taille de la zone de données couverte par le segment à l'intérieur du fichier.
p_memsz:	Indique la taille de la zone de données couverte par le segment dans la mémoire.
			NOTE: Lorsque p_memsz est supérieur à p_filesz pour un segment PT_LOAD, l'espace supplémentaire en mémoire est initialisé à zéro.
			C'est notamment le cas des données non initialisées (.bss). Cette technique évite de stocker inutilement dans le fichier des octets
			dont on sait qu'ils devront être initialisés à zéro. Memsz ne peut pas être inférieur a filesz.
p_flags:	Pour les segments PT_LOAD, indique les permissions mémoire demandées lors du chargement (read/write/execute).
			Ces permissions s'appliquent aux pages mémoire couvrant le segment et peuvent ensuite être modifiées, notamment avec mprotect().
			Durant le runtime, une operation a une adresse a l'intérieur d'une page qui ne possède pas les permissions correspondantes
			se verra refusée par le kernel (qui enverra un segfault au processus).
			Pour d'autres types de Program Headers, ces flags peuvent avoir une signification différente (comme PT_GNU_STACK), ou être simplmement ignorés
			(comme PT_PHDR, PT_INTERP, PT_DYNAMIC...).

p_align:	Nous expliquerons ce champs plus en détails plus tard.

Quelques exemples pour s'assurer que tout est clair :
- ProgramHeader[0] est de type PHDR. On sait donc qu'il decrit un segment qui va contenir toutes les entrées de la Program Header Table. Le segment commence au 0x40eme bytes
  du fichier, et occupe 0x2d8 bytes. Dans l'image finale chargée en mémoire, ce segment sera à l'adresse virtuelle 0x400040, et aura la même taille que dans le fichier (0x2d8).
  Ici, bien que le flag Readonly soit set, celui-ci n'a aucun impact sur les permissions mémoire, car ce Program Header ne provoque pas lui-même de mapping.
  Ses données sont néanmoins présentes en mémoire puisqu'elles sont englobées dans un segment PT_LOAD.

- ProgramHeader[2] est de type PT_LOAD. On sait que ce segment va être chargé en mémoire. Il comprend l'intervalle [0x00-0x908) du fichier ELF. On voit donc qu'il englobe notamment
  le Header de l'ELF et les segments PHDR et INTERP. En mémoire il se trouvera à l'addrese 0x400000, et aura la même taille que dans le fichier. Ici le flag Readonly est appliqué
  lors du mapping comme permission de base du segment (ces permissions peuvent ensuite être modifiées avec mprotect()).

- ProgramHeader[5] a la particularité d'avoir un memsz supérieur a son filesz, on sait donc que ce segment en mémoire sera plus grand que le segment dans le fichier, et que l'espace
  supplémentaire sera initialisé a 0 (bss).

- ProgramHeader[11] est de type GNU_STACK. Ce type de Program Header ne decrit pas un segment, mais sert a indiquer au kernel quelles la mémoire représentant la Stack du processus
  (qui est egalement un espace memoire attribué par le kernel au demarrage d'un processus, nous y reviendrons) doit être executable ou non. Ici rien n'est donc chargé, le champ p_flag est utilisé
  pour renseigner cette information via le champ p_flag les autres champs sont ignorés.

Nous avons desormais toutes les briques necessaires pour comprendre comment le système charge et execute un ELF.

Chargement d'un ELF

En parlant simplement, la premiere chose qu'il se passe lorsque le kernel recoit un appel systeme execve avec pour argument un ELF executable c'est qu'il trouve la Program Header Table
grace a l'Header du fichier et charge en mémoire les segment PT_LOADS.

Comme nous l'avons expliqué au debut, lors de l'execution d'un processus, un espace de memoire virtuelle est crée pour ce processus.

Le kernel va donc mapper autant de pages mémoire que nécessaire pour mapper tous les PT_LOADS.

le kernel utilise mmap(). Avec mmap() on peut indiquer un fichier a mapper et le mapping se fait par pages de fichier

Le mapping d'une page se fait avec l'appel systeme mmap. Cet appel permet deux types de mapping, le mapping de fichier et le mapping anonyme :
- Mapping anonyme: On demande simplemnt au kernel de mapper une taille de memoire vierge. Le kernel attribue donc assez de pages mémoire initialisées a 0 pour contenir la taille demandée.
  Ces pages mémoire sont complètement indépendantes et ne sont reliées a aucun fichier.
- Mapping par fichier: Dans ce cas on demande au kernel de mapper directement une portion du contenu d'un fichier sur disque, d'une certaine taille et à partir d'un offset précis.
  Le kernel va donc arrondir au page size inferieur pour le offset et au page size superieur pour a taille (a expliquer claierment).
